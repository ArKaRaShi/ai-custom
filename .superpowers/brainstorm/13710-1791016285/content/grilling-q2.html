🔥 Question 2: Concurrency & Atomic File Swapping (Torn Reads)

OMP and code editors are actively running in the background on your machine.

If an AI agent or language server (LSP) reads ~/.agents/skills/deep-research/ at the exact second you run sync pull --apply:

If we copy files one-by-one in-place, the agent could read the new SKILL.md while still reading old helper scripts (a "torn read"), causing unexpected runtime crashes or hallucinated errors!

RECOMMENDED (POSIX ATOMIC RENAME)
A

Atomic Staging + POSIX Rename

Stage in temp folder, then atomic directory swap

  • Write files to sibling temp directory: ~/.agents/skills/.tmp-deep-research/.
  • Execute atomic rename: fs.renameSync() (POSIX rename is instant: <1ms).
  • Result: An agent reading the folder either sees 100% old version or 100% new version. Impossible to experience a torn read.
B

Process File Lock (.lock file)

Acquire a lockfile during sync

  • Create .ai-sync.lock while syncing. Other processes wait.
  • Trade-off: External tools (like VS Code or simple shell commands) don't check our lockfile, so they can still read partial files.
C

Direct In-Place Overwrite (The Old Way)

Copy files directly into existing folder

  • Simplest code, but vulnerable to torn reads if a file transfer is interrupted mid-flight.
